Designing Horizon Bank Developer Central

Accelerating the developer lifecycle through modular architecture and self-service utility.

Senior Product Designer · 4 Months

error

Problem

Engineering tools, documentation, and compliance processes were scattered across fragmented SharePoint sites, creating a steep learning curve and constant support load on lead engineers.

lightbulb

Solution

Consolidated developer workflows into a single portal organized around four tasks — Discover, Build, Learn, Manage — with interactive sandbox editors, API exploration, and code generators built in.

trending_up

Impact

Onboarding dropped from weeks to days and integration bugs fell 35%. A later AI phase (below) focuses on reducing setup effort, minimizing repetitive support dependency, and accelerating MFE adoption.

Project Overview

Horizon Bank Developer Central replaced a set of fragmented internal tools with a single, self-service developer experience. The legacy setup caused real friction — in onboarding, and in the daily work of thousands of internal engineers.

Objectives

  • Unify the toolchain — one source of truth for APIs, documentation, and infrastructure management, replacing scattered internal sites.
  • Enable self-service — reduce dependency on central support with intuitive, automated tools for scaffolding and deploying code.
  • Support the architectural shift — help the org move from monolithic legacy systems to modular Micro-Front-End (MFE) architecture through clear governance and discoverable components.

Methodology

I ran a standard five-phase process — Empathise, Define, Ideate, Design, Test — adapted for enterprise technical constraints, so every architectural decision traced back to an actual developer workflow rather than an assumption about one.

1. Empathise: Understanding the Developer Context

I ran contextual inquiry sessions with 10 developers across seniority levels, watching them work through standard platform tasks in real time rather than relying on what management assumed the problems were.

What I asked

  • "Walk me through your exact process when discovering and integrating a new internal API."
  • "Where do you go when the official documentation fails to resolve your implementation blocker?"
  • "Describe the biggest bottleneck you face when attempting to spin up a new local environment using the current reference app."
  • "How do you currently track versioning changes for dependencies across the monolithic repository?"

What developers were dealing with

Steep learning curve for MFE

No structured onboarding for the shift to modular architecture — developers reverse-engineered documentation written for senior architects, and error rates on initial setup were high.

Fragmented connectivity

Tools, compliance forms, and API docs were spread across inconsistently branded SharePoint sites. Context-switching was a major source of cognitive load.

Outdated documentation

Written guides lagged behind the platform's actual capabilities, so developers trusted informal knowledge-sharing over official docs.

Support gaps

Heavy reliance on synchronous Teams support meant lead engineers spent significant time as ad-hoc support agents instead of doing their own work.

One concrete data point: developers waited up to three weeks for environment configuration and documentation access before writing their first API call, and mismatched sandboxes meant 20% of code failed in staging purely from local environment variance.

3. Ideate: Structuring the Solution Architecture

The big ideas

Automated code scaffoldingA CLI-backed UI generating boilerplate React components pre-configured with enterprise security standards and design tokens.
Integrated sandbox editorsAn in-browser IDE for API testing and component playground work, no local environment required for initial evaluation.
Unified API explorationInteractive endpoint documentation allowing engineers to discover APIs and test payloads without switching platforms.
Version switchingA persistent global toggle between API versions and documentation states without losing your place.

I rebuilt the information architecture around a task-based taxonomy instead of an org-chart one: Discover, Build, Learn, Manage. Tree-testing with senior engineering leads confirmed the model held up.

4. Design: From Wireframes to High-Fidelity Execution

Wireframes focused on layout and module hierarchy, with a strict modular grid to handle dense data tables, long code blocks, and multi-pane navigation. The north star metric during this phase was "time to first Hello World" — landing page to a working boilerplate download in under three clicks — validated with engineering stakeholders against what the backend could actually support.

The final visual system uses a mostly monochromatic palette with brand accents reserved for interactive states and status indicators. Typography splits by job: 'Inter' for dense, data-heavy UI, and [second typeface — fill in] for long-form documentation, chosen for a more editorial reading experience. Modal windows, nested dropdowns, and terminal-style code blocks all got documented interaction specs, with spacing and structural annotations precise enough for the dev team to implement pixel-for-pixel.

The core problem with documentation: Scattered across PDF specs and Confluence, with no live playground — developers had to deploy to staging just to check a payload response. Building an integrated, live code sandbox let engineers validate API contracts in real time instead, which cut integration bugs by 35%.

Phase 2 — Evolving Developer Central with AI

Developer Central had solved for centralizing documentation, tools, and onboarding. But research surfaced a deeper problem: developers weren't stuck because information didn't exist — they were stuck because finding it, and turning it into working code, took real effort. The next step wasn't more documentation navigation — it was AI embedded directly into the workflows developers already used, not another standalone tool.

What the research showed

Insight 01

"I need ready-made code to start faster."

New developers lost real time configuring environments, learning COSMOS dependencies, and hand-writing boilerplate before touching actual business logic.

Insight 02

"I know the documentation exists. I just can't find it."

Resources were split across COSMOS, API docs, GitHub, migration guides, and internal learning platforms — developers spent more time searching than building.

That pointed to two opportunities: AI-assisted MFE code generation, to remove the "getting started" bottleneck, and semantic search, to help developers find answers instead of documents.

Solution 01

AI-Assisted MFE Code Generation

Project setup was the most painful moment in the journey — configuring dependencies, understanding COSMOS architecture, and manually scaffolding Micro Frontends before writing a first line of real code. Rather than build a separate AI tool, I extended the existing MFE Generator already inside Developer Central:

Solution 02

Semantic Search & Intelligent Discoverability

Developers already knew the documentation existed — the problem was knowing where to look, since keyword search required knowing document names and repo structure in advance. The fix was replacing keyword search with semantic understanding: the existing global search bar became an AI-powered knowledge assistant.

Ask it something like "How do I change a button to Standard Skin in React?" and instead of a list of files, it returns a synthesized answer with the relevant code snippet, a link to the exact COSMOS component, and related migration guides — pulling from the COSMOS component library, API registry, migration docs, and release notes.
